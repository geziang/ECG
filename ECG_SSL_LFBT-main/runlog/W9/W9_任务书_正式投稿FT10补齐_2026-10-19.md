>
> **执行主机**：仅限主机 A（`Win4090`，RTX 4090 24 GiB，conda `DL`，PyTorch 2.5.1+cu121）。当前办公机缺少正式数据、预训练 checkpoint 和 `DL` 环境，不得在办公机降配复现后混入论文。
>
> **核心原则**：不重新预训练、不搜索超参数、不依据 test 结果选配置；只复用已经冻结并完成 SHA 审计的 encoder，补做缺失的 clean FT10 下游评估。W1–W8、JOINT、ABC 既有账本只读，新产物统一写入 `runlog/W9/`。

## 一、为什么必须补这一批

主论文表 4 的外部基线 FT10 尚有 5 个数据集—方法单元格为空：SimCLR/SimCLR+NSTDB/TSR 的 Chapman，以及 CLOCS 的 CPSC 和 Chapman。空格来自历史任务范围不同，并非结果遗漏。正式投稿若保留不规则空格，容易被质疑选择性报告。

此外，主论文当前明确承认 M2（LFBT+Beat-RR）和 M5（LFBT+NSTDB）的 CPSC/Chapman FT10 未运行。若目标是“本批实验结束即可成稿”，这 4 个内部单元格也应在同一冻结协议下闭合。因此本批分为两部分，均为正式投稿必做项：

1. **P0：外部基线缺格**，5 个单元格 × 3 seeds = 15 次 FT10；
2. **P1：内部矩阵闭合**，M2/M5 × CPSC/Chapman × 3 seeds = 12 次 FT10。

合计 **27 次正式 FT10**。全部复用已有预训练 checkpoint，禁止开启新的 PT 任务。

## 二、冻结评估协议

所有 27 次运行逐字沿用既有 `run_ft.py` 协议：

| 项目 | 冻结值 |
|---|---|
| 任务 | clean FT10，全参数微调 |
| 标签比例 | `--fraction 0.1` |
| 随机种子 | `{0,2,4}` |
| epoch | `100` |
| batch size | `128` |
| optimizer | Adam |
| learning rate | `0.0001` |
| workers | `4`；资源冲突时只能降低 workers，不得改变其他训练参数 |
| checkpoint 选择 | 每个 epoch 只按 validation loss 选择最优 checkpoint |
| 测试集 | 最优 validation checkpoint 对 test 单次评估 |
| 指标 | macro-AUROC、macro-AUPRC；同时保存现有扩展指标 |
| 预测 | 必须保存逐记录 `y_true.npy`、`y_pred.npy`、`y_prob.npy` 和 `metrics_ext.json` |
| 架构开关 | 全部与预训练 checkpoint 的 `config.json` 一致；本批涉及模型均为 `--trc 0` |
| 调参 | 禁止；任何异常只做实现诊断，不以 test 结果更换超参数或种子 |

10% 训练子集继续由现有加载器使用相应 seed 的固定随机划分生成。不得提前物化另一份 10% 子集，也不得改变类别映射、样本顺序或 train/val/test 目录。

M5 的 NSTDB 仅属于预训练增强；本批 FT10 和 test 均为 clean 输入。不得在 M5 下游训练中再次注入 NSTDB。

## 五、主机 A 代码交付要求

主机 A 自行实现代码，建议但不强制采用以下文件名：

```text

  tests/ 或 tests/test_w9_*.py   # 门禁与幂等测试
```

代码必须满足：

1. **幂等断点续跑**：只有结果账本、`metrics.json` 和四个预测工件全部存在且元数据一致时，任务才可跳过。
2. **逐任务原子落账**：并发车道不得共同无锁追加同一个 CSV；可先写每任务 JSON/分车道 CSV，收官时唯一键合并。
3. **唯一键**：`(method, seed, eval=ft10, dataset)`；最终不得重复。
4. **失败即停**：checkpoint/data/架构门禁失败、返回码非零、指标非有限、预测维度错误均停止相应车道并写 `events.md`。
5. **资源纪律**：最多双 GPU 车道，启动错峰至少 10 分钟；若显存或 IO 互相阻塞则退回单车道，不得降低 batch size 改变正式协议。
6. **Smoke 不碰 test**：正式任务前只允许 checkpoint 加载、一个 train batch、一个 val batch和输出维度检查；不得用 test 做 smoke。
7. **测试单发**：正式任务完成训练并选定 validation checkpoint 后，test 只评一次。异常复验不得覆盖原结果，须单列诊断记录并先说明原因。
8. **不修改冻结账本**：不得向 W4/W8/JOINT/ABC 的原始 CSV 追加行；W9 只引用其结果。

`metrics_ext.py` 当前预测目录守卫只允许 W3–W8、JOINT、ABC 路径。主机 A 应以“默认行为不变”的方式显式加入 `runlog/W9/`，并补单测证明：W9 允许、W2 仍拒绝、任意其他路径仍拒绝。不得把 W9 预测伪装写入 W8。

## 九、机时与执行顺序

按既有 FT10 约 30–35 分钟/任务估算，27 次单车道约 13.5–16 GPU 小时；双车道约 7–9 小时，另留 1–2 小时用于 preflight、汇总和核验。

建议顺序：

1. preflight + 无 test smoke；
2. P0 先跑 CLOCS-CPSC 三种子，再补四种方法的 Chapman；
3. P1 跑 M2/M5 的 CPSC 与 Chapman；
4. 完整性检查、均值/标准差汇总、表 4 草表；
5. 最终报告、commit、push、HOSTS 收官。

任务没有性能晋级门。即使某外部基线超过本文方法或某组件退化，也必须原样报告；本批唯一成功标准是协议一致、证据完整、账本可审计。
